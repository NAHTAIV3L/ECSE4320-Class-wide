1. Project 1 SIMD Profiling

1.1. Building and running:

./configure
ninja -j$(nproc)
./scripts/run_experiments.sh quick # could be full instead of quick.
./scripts/verify_vectorization.sh  # checks for widest vector usage
python ./scripts/plot_results.py   # plot the data generated from ./scripts/run_experiments.sh

1.2. Pre-experiment hypotheses:

  1. Using default and widest optimizations should increase throughput. This benefit should decrease as the set size increases because of using worse caches. This will eventually get to where the optimizations can't speed up the operation any faster because of RAM speed.
  2. Sequential operations should be faster than any set stride or gather operations. This should also converge because of the previous reason.
  3. Doing anything with float64 instead of float32 should be half as many GFLOPS but the same byte throughput.

1.3. Differing compilation options:

label compiler flags reasoning
Scalar -march=x86-64 -O2 -fno-tree-vectorize -fno-tree-slp-vectorize scalar baseline with optimisation enabled
Default -march=x86-64 -O3 -ftree-vectorize baseline x86-64 (SSE2, 128-bit) auto-vectorisation
Widest -march=native -O3 -mprefer-vector-width=256 -ffast-math -fno-math-errno widest ISA (AVX2, 256-bit) plus FP reassociation so reductions can vectorise

1.4. My computer specific info

My computer defaults to doing -march=x86_64-v3 so this has to be disabled. Also default optimizations are turned on while disabling vectorization optimizations. Also according to DeepSeek V4.1 Flash -ffast-math has to be used in widest for the compiler to optimize the dot product kernel.

I also have AVX2/AVX-VNNI as CPU flags. This allows for 265 bit registers but no 512 registers because I dont have AVX512. The file: ./results/env/environment.txt shows a more verbose version of my computer's environment. This environment is generated with ./scripts/capture_env.sh

1.6.4. Throughput vs alignment

A lot of SIMD instructions only allow loading memory from aligned bytes, so having the array be unaligned gives big performance penalties. which can be seen. These most likely happen at one byte from a 4 or 8 byte alignment. There are some SIMD instructions for loading from an unaligned address but I would assume that they are slower than the aligned loading ones. which could be a general slowdown that the compiler had to do because of the chance that the bytes are not aligned.

1.6.6. Stride

These all compare throughput vs stride. Having a stride any bigger than 1 is not good for performance because it increases cache misses. This then slows down the entire process because you hit the memory throttling much faster than a sequential walk. Because of this all three optimization levels compress much faster.
